# PTS Historical Restoration — Evidence Package

This document records what has been verified about the original BitShares PTS
(ProtoShares) DPoS genesis, and how. It makes no claim beyond what is shown
here. All source material is public and was retrieved from the official
GitHub history of the project.

## 1. Provenance chain

```
ProtoShares (PTS) PoW chain, final block #81688
  (blocktime 1418589857 unix = 2014-12-14 20:44:17 UTC)
    -> raw balance snapshot: pts-2014-12-14-snapshot.json.gz
         sha256: 85da0121480b0ab8297a5e700fcffc61741a021ceb0c740eefc3f3f5686ad2cd
    -> make-genesis.sh (combines snapshot balances + names.json delegate list)
    -> libraries/blockchain/genesis.json
         sha256: be2979054fbac18367b0740c0ebe35b1f02e3fb6ca692bce03412755f8fd1a83
         size: 3,081,292 bytes (~2.94 MB)
         internal timestamp field: "20141214T214417"
    -> committed as 92a40f2dec6acc73728c16d23a84631a66ca3c0e
         "Preliminary genesis 2.0", author Peter Conrad, 2014-12-14 22:24:38 +0100
    -> tagged v2.0 (2014-12-14 22:29:05 +0100) and v2.0.1 (2014-12-17 17:01:33 +0100)
         genesis.json is byte-identical across both tags
```

All commits, tags, and blobs referenced above are reachable in the public
history of `github.com/PTS-DPOS/PTS` and `github.com/bitshares/bitshares-pts`.
Nothing here was generated or invented for this project — every artifact is
a `git cat-file` extraction of an object that already existed in that public
history.

### Why the two timestamps differ by exactly one hour

The raw snapshot records `blocktime: 1418589857` (2014-12-14 20:44:17 UTC).
`make-genesis.sh` converts this with `date -d @$ts` on the machine that
generated the file, which was evidently set to CET (UTC+1) — producing
`20141214T214417`, the value embedded in genesis.json. This is a build-time
artifact of the generating machine's local timezone, not a discrepancy in
the data itself.

## 2. What the genesis.json actually contains

- `balances`: 55,044 entries (address, raw-unit balance)
- `names`: 114 entries (delegate name, owner address, pay rate) — real
  usernames such as `cyrano`, `pc`, `bitcube`, `fftt`, `lafona`, `alphabar`,
  `wackou`, `riverhead` match historical BitSharesTalk forum accounts.
- Raw balance sum: 176,359,437,874,154 units. With
  `BTS_BLOCKCHAIN_PRECISION = 1,000,000` (6 decimals), the naive balance-only
  total is ~176.36M PTS — this is NOT the same as total supply (see below).

## 3. Independent build and verification

Source: `v2.0.1` tag, built with historically-matched dependencies rebuilt
from source (not the modern system toolchain) to avoid any behavioral drift
in cryptography or serialization:

- **Boost 1.54.0** (built from `archives.boost.io`, matching the
  `BUILD_UBUNTU.md` era) — required for `fc::thread`'s cooperative scheduler,
  which uses a Boost.Context/Coroutine API removed in later Boost versions.
- **OpenSSL 1.0.1h**, 5 Jun 2014 (built from `openssl.org/source/old`) —
  required because `base58.cpp` uses direct `BIGNUM` struct access and
  `BN_init`, both removed when OpenSSL 3.x made `BIGNUM` opaque.

All patches needed to compile this 2014 codebase with a modern host compiler
(GCC 13) are in `build-patches/`. None of them touch consensus logic — see
`build-patches/README.md` for the reasoning behind each one.

### Result: node initializes genesis correctly

```
blockchain_head_block_num: 0
blockchain_share_supply: "999,999,999.971611 PTS"
```

This total-supply figure — computed by the node from the genesis state, not
from a naive sum of the `balances` array — matches the historical circulating
/ total supply shown on the (dormant, "Preview Page") CoinMarketCap listing
for BitShares PTS (UCID 62): 999,999,386 PTS. The small residual difference
is consistent with rounding/dust and does not affect the conclusion: this
genesis file is the one the total-supply figures on record are describing.

The node ran its normal steady-state loop (p2p, wallet scanner, mail client
threads) for 5+ minutes with zero exceptions logged, confirming the ported
Boost.Context-based scheduler works correctly at runtime, not just at
compile time.

### Result: address derivation verified independently

A test keypair was generated by the built `pts_create_key` binary. The
resulting PTS address was then re-derived from scratch in Python (standard
`hashlib` + `ecdsa` library — no PTS/BitShares code involved), following the
algorithm read directly from `pts_address.cpp`:
`sha256(compressed_pubkey) -> ripemd160 -> version byte -> double-sha256
checksum -> base58`.

```
Computed pts address:  PYvLDeNVkH3yPCQSCqTbdxH8GBnm7MBfvt
Expected pts address:  PYvLDeNVkH3yPCQSCqTbdxH8GBnm7MBfvt
MATCH: True
```

This confirms the compiled cryptography produces historically-consistent
address output — i.e. a key that controlled a balance in 2014 would resolve
to the same address today.

## 4. What this evidence does NOT establish

- It does not identify or contact any historical delegate or balance holder.
- It does not constitute control over, or endorsement by, any historical
  BitShares PTS contributor.
- It does not mean a live network currently exists — no blocks have been
  produced beyond genesis; this is a static, offline verification only.
- The CoinMarketCap UCID 62 listing match is circumstantial (matching supply
  figures), not an official confirmation from CoinMarketCap.
